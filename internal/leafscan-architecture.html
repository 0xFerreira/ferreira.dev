leafscan / engineering note

LeafScan v2.0

edge daemon · C++20 · no exceptions · no RTTI
target NVIDIA Jetson · Basler · u-blox F9P
boot static memory · zero runtime alloc

LeafScan is a single binary that drives an agricultural sensor rig: cameras, LiDAR, GNSS, modem. Sensors emit signals onto a bus; detection workloads consume them and write back detections. The whole thing boots by probing what's plugged in, then resolves which workloads can actually run given the sensors that answered. No threads. No allocations after startup. One HTTP server for the dashboard.

01Pipeline

Sensors write, workloads read & write, dashboard observes.

02The model

Four nouns. Everything is one of these.

nounshapepurpose
Signal enum · 6 values · 1 byte The type of data flowing on the bus: Frame, Depth, Position, Connectivity, Detection, HwStats. New data type? New enum value.
Component POD struct of fn-pointers A driver or workload. Declares reads / writes / optional signals plus detect / start / stop hooks. There are nine of them, all listed in main.cpp at compile time.
Entity fixed slot, max 64 on the bus A named producer of one signal. cam0 writes Frame; citrus:cam0 writes Detection sourced from cam0. Double-buffered (buf[2] + front) with monotonic seq and timestamp_ns. Each entity owns its own tick + interval_ms.
Bus flat array of entities + arena pointers The whole shared-memory world. No locks: writers flip front after filling the back buffer; readers take a snapshot of (front, seq). That's the synchronisation.

04Boot & runtime

Two phases at startup, then a single scheduler loop forever.

Resolver — resolve.cpp

1
Detect. For every component, call detect(). Hardware probes succeed or fail; software components (no detect fn) are always available.
2
Start, in rounds. Loop over detected components. A component starts only when every reads signal already exists on the bus. Starting it registers entities → unblocks the next round.
3
Mark stragglers. Whatever is still Detected after no progress was made gets DepsMissing (e.g. avocado without ouster).

Topological start without an explicit DAG — the bus is the dependency graph. Cheap, and you can hot-add a component by adding one line to main.cpp.

Scheduler — scheduler.cpp

A single thread. After resolve, every entity with a non-null tick gets a slot (max 32). The loop wakes at the earliest deadline, fires every slot whose deadline has passed, recomputes the next deadline, sleeps again.

// no-drift sleep, kernel idles the core
clock_nanosleep(CLOCK_MONOTONIC,
                TIMER_ABSTIME,
                &next_deadline,
                nullptr);

Falling behind is non-fatal: deadline jumps to now + interval rather than catching up frantically. Idle root entities (e.g. a camera with no consumer) are deliberately not scheduled.

05Memory

Three static byte arrays, three bump arenas. Allocation ends before the run loop starts.

frames
32 MB
detections
1 MB
scratch
4 MB

All three live in .bss (declared as static uint8_t pool[N] in main.cpp). The Arena bump-allocator hands out aligned, zeroed slices from each pool when components register entities. Once resolve() returns, the .bss footprint is whatever it is — and stays that way.

Compile flags: -fno-exceptions -fno-rtti -Wall -Wextra -Wpedantic. The Component contract uses raw function pointers and std::span, no virtual dispatch.

06Dashboard API

An HTTP server thread alongside the scheduler. Serves the SPA and a few read-only routes. stubbed — server_start() currently just logs; no socket, no routes wired.

07How to think about it

If you're patching this codebase tomorrow.

  • Want a new sensor? Add a Component with writes = {Signal::X}. Implement detect / start / stop / tick. Register it in main.cpp.
  • Want a new workload? Same shape, but reads = {…}. The resolver handles ordering; you don't.
  • Want a new data type? Add a value to the Signal enum and a metadata struct to the Entity::meta union.
  • Synchronisation: writers fill the back buffer, then flip front and bump seq. Readers snapshot front and read buf[front]. No mutex, single-threaded scheduler.
  • What runs at runtime? Just the scheduler loop and the HTTP server. No allocations, no exceptions, no surprises.
